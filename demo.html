Website Integration

Add PixelShield to your website

Two files, two steps. Works on any static site, WordPress, Squarespace, Webflow — anywhere you can add HTML and upload files.

1
Upload pixel-shield.js to your website's root (or any public folder).
2
Upload your encrypted image (the one you made in the "Encrypt Your Image" tab).
3
Add two attributes to your existing <img> tag and include the script once.

The HTML you need

<!-- Your protected image -->
<img
  src="encrypted-photo.png"      <!-- encrypted file on your server -->
  data-pixel-shield              <!-- marks this image for auto-decrypt -->
  data-seed="3735928559"         <!-- your secret seed number -->
  alt="My artwork"
  width="800"
>

<!-- Add once, just before </body> -->
<script src="pixel-shield.js"></script>

Multiple images, one script

<!-- Each image can have its own seed -->
<img src="photo1-encrypted.png" data-pixel-shield data-seed="11111111" alt="Photo 1">
<img src="photo2-encrypted.png" data-pixel-shield data-seed="22222222" alt="Photo 2">
<img src="photo3-encrypted.png" data-pixel-shield data-seed="33333333" alt="Photo 3">

<!-- One script tag handles all of them -->
<script src="pixel-shield.js"></script>

Limitations to know

Limitation Details
Social media Doesn't protect images you upload to Instagram, X/Twitter, TikTok. Those platforms re-host the file on their CDN and never run your JS.
Headless browsers A sophisticated scraper running a full headless Chrome would execute the script. Mitigation: obfuscate pixel-shield.js and move the seed server-side.
CORS The encrypted image must be on the same domain OR served with Access-Control-Allow-Origin: *. Same-origin always works.
No server required Encryption/decryption is 100% client-side. The seed travels in HTML — keep it out of public GitHub repos if you want maximum security.
Technical Details

The encryption algorithm (V14)

Four years of iteration led to a formula that is mathematically perfect: 0% error rate, infinite PSNR, and near-maximum entropy in the encrypted output.

The gap we exploit

1
AI scrapers don't run JavaScript. They send an HTTP GET to the image URL and save the bytes.
2
We store scrambled pixel data at the image URL. The raw PNG is unusable noise.
3
Your visitor's browser runs our script, silently unscrambles the pixels, and displays the real image.
4
The scraper never knows the image was protected. It just downloads what it thinks is a real image — and trains on noise.

The V14 formula

// PRNG: xorshift32 — deterministic, different key for every pixel
function seededPRNG(seed) {
  let s = seed >>> 0;
  return () => {
    s ^= s << 13;  s ^= s >> 17;  s ^= s << 5;
    return (s >>> 0) & 0xFF;
  };
}

// ENCRYPT — run once, store result on server
for (pixel of pixels) {
  const kr = rng(), kg = rng(), kb = rng();  rng(); // 4 keys per pixel
  encrypted.R = original.G ^ kr;  // swap channels + XOR key
  encrypted.G = original.B ^ kg;
  encrypted.B = original.R ^ kb;
  encrypted.A = 255;              // always opaque
}

// DECRYPT — run in browser, identical seed = perfect recovery
for (pixel of encryptedPixels) {
  const kr = rng(), kg = rng(), kb = rng();  rng(); // same PRNG sequence
  decrypted.R = encrypted.B ^ kb;  // un-XOR then un-swap
  decrypted.G = encrypted.R ^ kr;
  decrypted.B = encrypted.G ^ kg;
  decrypted.A = 255;
}

Why XOR is perfect

The old V10 formula used division chains that lost precision through floating-point rounding. XOR has none of that — it is a bitwise operation with an exact inverse:

a XOR key = b    →    b XOR key = a   (always, with no precision loss)

Channel scrambling adds structural disruption on top:
  R goes to the B slot → pixel colour relationships are destroyed
  G goes to the R slot → spatial patterns unrecognisable to AI
  B goes to the G slot
